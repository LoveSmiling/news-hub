## 上下文

NewsHub 已有 2000+ 条新闻数据（11 个源），但 embedding 字段全部为空，keywords 仅部分覆盖。Chat RAG 向量搜索无法命中内容，只能回退到关键词搜索，严重影响 AI 对话质量。需要建立自动化的 embedding 生成流水线和管理界面。

当前技术栈：Python/FastAPI/SQLAlchemy async + Vue 3/Naive UI，bge-m3 embedding 模型（1024 维），pgvector 扩展，单 Docker 实例部署。

## 目标 / 非目标

**目标：**
- 采集时自动为所有新条目生成 embedding 和 keywords
- 提供知识库概览（总量、覆盖率、按源分布）
- 支持语义搜索（输入查询 → 向量相似度排序）
- 支持增量更新（处理无 embedding 的条目）和全量重建
- 后台任务有进度追踪，前端实时显示

**非目标：**
- 不引入独立知识库表（复用 hot_items）
- 不引入 Celery/Redis（内存任务管理即可）
- 不支持自定义知识条目上传（未来可扩展）
- 不做 embedding 模型切换/管理（使用现有 ai_configs 体系）

## 决策

### D1: Embedding 输入文本 — `title + clean(summary)[:500]`

**选择**：拼接标题和清理后的摘要（截断 500 字）作为 embedding 输入。

**考虑的替代方案**：
- 仅 title（~20 字）：太短，语义信息不足，无法区分同类新闻
- title + keywords：keywords 是离散标签，对连续语义空间帮助有限
- 全文 summary：平均 ~170 字，最长 ~500 字，在 bge-m3 的 8192 token 窗口内完全可行

**理由**：title 放前面（bge-m3 对开头权重更高），summary 补充语义上下文。截断 500 字平衡信息量和计算开销。

### D2: 后台任务管理 — 内存任务管理器

**选择**：`kb_task_manager.py` 使用内存 dict 存储任务状态，asyncio.create_task 执行。

**考虑的替代方案**：
- Celery + Redis：功能强大但引入两个新依赖，单实例部署过重
- 数据库任务表：持久化好但增加迁移和查询复杂度
- APScheduler job：已有但不适合一次性任务

**理由**：单实例部署，重启后任务丢失可接受（重新点击即可），保持简单。

### D3: 采集自动化 — 在 scheduler jobs 中集成

**选择**：在 `collect_source()` 完成后调用 `_enrich_embeddings()` 为本批次生成 embedding。

**理由**：每次采集约 30-50 条新闻，bge-m3 批量 embedding ~5 秒，不会显著拖慢采集周期。同时取消 keywords 的前 10 条限制，改为全覆盖。

### D4: 批量处理策略 — 每批 50 条

**选择**：embedding 批量处理以 50 条为一批，任务管理器逐批更新进度。

**理由**：bge-m3 单批 50 条约 2-3 秒，2000 条约 2 分钟完成。批次间更新进度，前端每 2 秒轮询。

### D5: API 设计 — 异步任务模式

**选择**：POST /api/kb/tasks 返回 202 + task_id，GET /api/kb/tasks/{id} 轮询进度。

**考虑的替代方案**：
- WebSocket：实时性好但实现复杂，nginx 需额外配置
- SSE：可行但任务管理场景下轮询更简单

**理由**：轮询实现最简单，2 秒间隔足够流畅，与现有技术栈一致。

## 风险 / 权衡

- **[风险] embedding 服务不可用** → 采集仍正常完成，embedding 生成失败仅记录日志，后续可通过管理页面增量补建
- **[风险] 全量重建期间内存占用** → 逐批处理（50 条/批），不一次性加载全部数据到内存
- **[风险] 重启后任务丢失** → 可接受，管理页面重新触发即可；stats API 实时计算覆盖率
- **[权衡] 内存任务 vs 持久化** → 选择简单性，牺牲持久化；未来规模扩大可迁移到数据库任务表
