## 需求
### 需求:RSSHub 数据源集成
系统必须通过自建 RSSHub 实例采集各平台热榜数据。采集器必须解析标准 RSS/Atom 格式的 Feed，提取标题、链接、热度值等信息并存入数据库。

#### 场景:正常采集 RSS Feed
- **当** 调度器触发某数据源的采集任务
- **那么** 系统必须向 RSSHub 发起 HTTP 请求获取该源的 RSS Feed，解析 XML 内容并提取所有条目信息

#### 场景:RSSHub 服务不可用
- **当** RSSHub 实例无法访问或返回错误
- **那么** 系统必须记录错误日志并在下一个调度周期自动重试，禁止因单个源失败导致其他源的采集中断

### 需求:YAML 配置驱动的数据源管理
系统必须通过 `sources.yaml` 配置文件管理所有数据源。每个数据源的配置必须包含名称、显示名称、分类、类型、RSSHub 路由和调度频率等字段。数据源类型必须支持 `rsshub`、`rss` 和 `custom` 三种类型。`custom` 类型的数据源禁止要求 `route` 字段，`route` 字段对 `custom` 类型为可选。

#### 场景:从配置加载数据源
- **当** 系统启动时
- **那么** 系统必须读取 `sources.yaml` 并为每个已配置的数据源注册定时采集任务

#### 场景:新增数据源
- **当** 管理员在 `sources.yaml` 中添加一个新的数据源配置
- **那么** 系统在下次加载配置时必须自动注册该源的采集任务，无需修改代码

#### 场景:加载 custom 类型数据源
- **当** `sources.yaml` 中存在 `type: custom` 的数据源
- **那么** 系统必须通过自定义爬虫加载机制处理该源，禁止因缺少 `route` 字段而报错

### 需求:定时调度采集
系统必须使用 APScheduler 按照每个数据源配置的 cron 表达式定时触发采集任务。

#### 场景:按频率定时采集
- **当** 某数据源配置的调度时间到达
- **那么** 系统必须自动执行该源的数据采集任务

#### 场景:多源并行采集
- **当** 多个数据源的调度时间同时到达
- **那么** 系统必须并行处理这些采集任务，禁止串行阻塞

### 需求:数据去重
系统必须对采集到的热榜条目进行去重，避免同一条目在同一采集周期内重复入库。

#### 场景:同一条目重复出现
- **当** 某条目的 URL 和来源与数据库中最近一次采集记录相同
- **那么** 系统必须跳过该条目，不重复插入

#### 场景:同一条目在不同采集周期出现
- **当** 某条目在新一轮采集中仍然在热榜上
- **那么** 系统必须更新其排名和热度值，而不是创建新记录

### 需求:按来源分类存储
系统必须为每条热榜数据标记来源标识（如 `weibo`、`zhihu`），并通过数据库索引支持按来源高效查询，实现数据溯源。

#### 场景:存储带来源标记的数据
- **当** 采集器成功解析一个 Feed 条目
- **那么** 系统必须将该条目连同来源标识、分类、原始数据（JSONB）一起存入 `hot_items` 表

#### 场景:按来源查询历史数据
- **当** 用户查询某个特定来源的历史采集记录
- **那么** 系统必须通过 `source` + `collected_at` 索引高效返回按时间倒序排列的结果

### 需求:采集后自动生成embedding
采集调度器在完成数据入库后，必须自动为本批次所有新条目生成 embedding。

#### 场景:采集新数据
- **当** 定时任务从某个源采集到 30 条新数据并保存到 hot_items
- **那么** 自动调用 embedding 批量生成服务，为这 30 条全部生成 embedding

#### 场景:embedding生成失败
- **当** embedding API 不可用或超时
- **那么** 记录警告日志，采集任务本身正常完成（不阻塞采集流程），条目的 embedding 保持 NULL

### 需求:采集后自动生成keywords全覆盖
采集调度器必须为本批次所有新条目生成 keywords，取消当前仅前 10 条的限制。

#### 场景:全量keywords生成
- **当** 定时任务从某个源采集到 30 条新数据
- **那么** 为全部 30 条生成 keywords（而非仅前 10 条）

#### 场景:keywords生成失败
- **当** LLM API 不可用
- **那么** 记录警告日志，不阻塞采集流程
